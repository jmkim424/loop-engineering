# /spec-new — 요구사항 → SPEC 초안

요구사항: **$ARGUMENTS**

이 커맨드는 **문서 한 장만** 만든다. 어떤 상황에서도 산출물 코드를 쓰거나 고치지 않는다.
`tetris-loop-workshop/` 안의 파일을 건드리면 이 커맨드는 실패한 것이다.

## 절차

### 1. 맥락 읽기

- `CLAUDE.md` — 기술 제약과 경계.
- `MEMORY.md` — 지금까지 무엇이 만들어졌는지, 열린 질문이 무엇인지.
- 기존 `SPEC_*.md` 전부의 frontmatter와 §5(범위 밖) — 번호, 의존 관계, 이미 다룬 범위를 파악한다.

요구사항이 비어 있으면(`$ARGUMENTS`가 없으면) 무엇에 대한 SPEC인지 사용자에게 묻고 멈춘다.

### 2. 크기 판정

한 번의 `/spec-run` 루프로 끝날 크기인지 먼저 판단한다.

- 완료 조건이 12개를 넘거나, 서로 독립적인 기능이 2개 이상 섞여 있으면 **분할한다**.
- 이번 SPEC에 담을 것과 후속 SPEC으로 미룰 것을 나누고, 미룬 것은 §5 "범위 밖"에 적는다.
- 분할했다면 이번 실행에서는 **첫 번째 SPEC만** 파일로 만들고, 나머지는 제목만 제안한다.

### 3. 번호와 의존 관계

- 기존 `SPEC_*.md`를 스캔해 다음 번호를 쓴다. 파일명은 `SPEC_NN_<slug>.md`.
- 이 SPEC이 전제하는 선행 SPEC을 `depends_on` 배열에 넣는다.
- `max_iterations`는 기본 `3`. 더 복잡하면 최대 `5`까지, 이유를 §1에 한 줄로 적는다.

### 4. 문서 작성

`SPEC_00_PROJECT.md`와 **동일한 형식**을 지킨다. 절을 빼거나 순서를 바꾸지 않는다.

```markdown
---
id: SPEC_NN
title: <한 줄 제목>
depends_on: [SPEC_00]
max_iterations: 3
---

# SPEC NN — <제목>

## 1. 목표
## 2. 기술과 파일 구조
## 3. 화면 정의
## 4. 상태와 공개 함수
## 5. 범위 밖
## 6. 완료 조건
## 7. 자동 검증
## 8. 수동 검증
## 9. 안전과 정지 조건
```

절별 규칙:

- **§1 목표** — 이번 단계가 만드는 것 한 문단. "이번 단계에서는 ~를 구현하지 않는다"를 함께 적는다.
- **§2 기술과 파일 구조** — `CLAUDE.md`의 기술 제약과 모순되면 안 된다. 파일이 추가되면
  왜 필요한지 적고, 추가 없이 가능하면 추가하지 않는다.
- **§3 화면 정의** — 화면에 나타나는 텍스트를 그대로 인용한다. "적절히", "보기 좋게" 금지.
- **§4 상태와 공개 함수** — `globalThis.TetrisGame`에 추가/변경되는 상수와 함수를
  이름·인자·반환값까지 적는다. 화면만 바뀌는 SPEC이면 "이번 SPEC에서 변경 없음"이라고 적는다.
- **§5 범위 밖** — 반드시 채운다. 비워 두지 않는다.
- **§6 완료 조건** — 아래 규칙을 따른다.
- **§7 자동 검증** — 브라우저 없이 확인 가능한 항목만.
- **§8 수동 검증** — 사람이 브라우저에서 밟을 절차를 번호 순서로.
- **§9 안전과 정지 조건** — SPEC_00 §9를 기준으로 하고, 이번 SPEC 고유의 위험을 추가한다.

### 5. 완료 조건 작성 규칙

- 체크박스 `- [ ]`로 쓴다.
- 한 줄에 하나의 관찰 가능한 사실만 담는다. "그리고"로 두 사실을 묶지 않는다.
- 줄 끝에 검증 수단 태그를 붙인다.
  - `(AUTO)` — 파일 내용 검사, 문법 검사, node에서 `game.js`를 로드해 확인 가능한 것.
  - `(HUMAN)` — 브라우저 렌더링, 콘솔 오류, 반응형, 시간 경과 후 상태, `test.html` 화면 결과.
- 두 태그 어느 쪽으로도 확인할 수 없는 조건은 **넣지 않는다**. 확인 불가능한 조건은
  루프를 영원히 끝나지 않게 만든다.
- "구현되어 있다", "잘 동작한다" 같은 문장 금지. 무엇을 보면 그렇다고 판정하는지 쓴다.

### 6. 추측 금지

요구사항에서 유추할 수 없는 값은 **임의로 정하지 않는다**. 예: 색상 코드, 폰트, 여백 수치,
애니메이션 속도, 점수 공식, 키 배치, 문구.

이런 값이 나오면 문서 맨 위 frontmatter 바로 아래에 블록을 만든다.

```markdown
> **[사람 확인 필요]**
> - 상태 패널의 배경색 — 지정되지 않음
> - 하드 드롭 점수 계산식 — 지정되지 않음
```

그리고 본문에는 해당 항목을 `[사람 확인 필요]`로 남긴 채 둔다. 임시값을 넣고 진행하지 않는다.

## 출력

파일을 만든 뒤 사용자에게 다음을 보고한다.

1. 만든 파일 경로와 `id` / `title` / `depends_on` / `max_iterations`
2. 완료 조건 목록과 각 항목의 `AUTO` / `HUMAN` 개수
3. `[사람 확인 필요]` 목록 (없으면 "없음")
4. 분할을 제안했다면 후속 SPEC 제목들
5. 다음 명령 안내: `/spec-run SPEC_NN_<slug>.md`

`MEMORY.md`는 이 커맨드에서 갱신하지 않는다. 새 SPEC의 존재는 `/spec-run`이 처음 실행될 때
기록된다.
